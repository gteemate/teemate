How TeeMate is built

What the app is made of, where it runs, how many databases there are, and how a change gets from here to members’ phones. In plain words, with the real numbers.

1web app, for phones, iPads and computers
2databases: test and live, the same shape
35tables in each database
~1,800automatic checks before each release
In one line: TeeMate is a single website written in plain JavaScript (no app store, no framework). It keeps all the club’s data in a Postgres database run by Supabase, and is hosted for free on GitHub Pages. There are two copies of the database: a test one to try changes on, and the live one members use.

The pieces and how they connect

Members’ phonesThe app in the web browser, or added to the home screen like an app. Works on iPhone and Android.
The club office iPadThe same app, signed in with the office login: it opens on the office pages.
The website (GitHub Pages)The app’s files: one page, the JavaScript, the styles and the course pictures. Free hosting. Address: gteemate.github.io/teemate
Supabase (live)The database with all the club’s data, sign-in, private photo storage, and the paper-scorecard reader.
Supabase (test)An identical copy with made-up data, where every change is tried first. Members never see it.
Claude (Anthropic)Reads paper scorecards: only the cropped score grid is sent, never names.
Open-MeteoThe weather at the course on Home. Free.
OpenStreetMapMap tiles for finding the course’s location. Free.

The phone talks to Supabase directly, with every request checked by the database’s own rules (below). The website itself holds no data: it’s the same files for every club member.

The two databases

Test (“teemate-test”)

  • Made-up club data that can be wiped and reloaded at any time (the seed and scenarios).
  • Every database change goes here first, and its database checks are run.
  • Where the real-browser screen checks run.

Live

  • What members use: today 139 members, 1,010 bookings, 130 scorecards, 6 events.
  • Changes only after they pass on test, and only with your go-ahead.
  • The demo logins (live@, admin@ and the rest, password “password”) live here too.

Both have the same 35 tables, kept in step by the numbered change files in supabase/migrations: each is applied once, to test then live, and recorded so it’s never applied twice. The seed and scenario scripts refuse to run on live.

Keeping data safe

  • The database decides, not the app. 47 row-level rules say who can see and change each row (a member sees their own requests; only players on a card can change it; only the office can delete a member). The app can’t get round them, even if someone tampers with it.
  • Anything with rules goes through a database function (130 of them): booking checks the two-hour gap and the release time; entering checks the closing date and places. Each refusal comes back as a plain message the app shows.
  • Secrets stay on the server. The phone only has the public key (which can do nothing the rules don’t allow). The Claude key is a Supabase secret, never in the app or the code.
  • Paper-card photos are cropped to the score grid on the phone first (names never leave it), kept in a private store that only the players on that card and the office can open.

Speed: what’s kept on the phone

Lists that rarely change (members, the course, events, competitions, club settings) are kept on the phone, so screens open instantly. The database stamps each kind of data when it changes; the phone checks the stamps and only fetches what’s changed. Tee times, scorecards and alerts are always fetched fresh. A small service worker keeps the app’s own files, so it opens quickly even on a poor signal.

How a change reaches members

1. Build itOn this computer, with a test written first for each change
›
2. Check it1,185 app tests, including every journey and every refusal
›
3. Test databaseDatabase changes applied to test; 599 database checks
›
4. Your go-aheadNothing goes live without it
›
5. Live databaseThe same change, then the checks again on live
›
6. PushGitHub runs every test again, builds the site and publishes it: live in about a minute

Members get the new version the next time they open or refresh the app. If the tests fail on GitHub, nothing is published.
